# CLAUDE.md

Guidance for working in this repo.

## What this project is, and where it's going

An interactive 3D relief map of downtown Macon: a hand-rolled Three.js scene with a free-roam camera (WASD + drag-look + Q/E for altitude), shipped as one self-contained HTML file (see `site/assemble.py`). It shares its data-prep pipeline with the sibling `macon-3d-print` repo (physically-printable STLs), but the two are expected to diverge. This repo previously ran on Google's `<model-viewer>` web component (orbit-only camera — look-at-target + distance + two angles, no way to translate through space), which was a dead end for "drive around the city" and got fully replaced. Next up:

- Eventually covering all of Macon, not just the downtown disk, with better building data (Overture Maps Foundation or Bibb County's own GIS, not just OSM) and toggleable stats overlays (Census ACS or similar).
- Real drivable-car physics — the current free-roam camera has terrain/building collision (see below) but no vehicle body, wheels, or momentum. A WASM physics engine (Rapier or Ammo.js) under Three.js is the natural choice when this happens; WASM is already proven in this project via both the Draco decoder and `three-mesh-bvh`'s accelerated raycasting.
- A full WASM game engine (e.g. Godot) was considered and explicitly rejected for now: its footprint (tens of MB before content) blows past what a self-contained single HTML file can reasonably hold, and it would badly hurt the Playwright-based screenshot/raycast debugging loop this project leans on heavily (see below). Worth revisiting only if this ever moves off the self-contained-single-file model entirely.

## Hard-won constraints — don't relearn these the hard way

**The page must be one self-contained HTML file with zero external network calls.** This was originally driven by publishing to a CSP-locked hosting environment (`connect-src 'self'`), which blocks not just cross-origin fetches but `fetch()` on `blob:` URLs too. Concretely:

- Three.js core + `GLTFLoader.js` + `DRACOLoader.js` + `BufferGeometryUtils.js` (a cross-dependency `GLTFLoader.js` needs) are vendored as plain files in `site/`, then embedded via an **import map** with `data:` URIs (`<script type="importmap">` mapping bare specifiers like `"three"` to `data:text/javascript;base64,...`) — this resolves `GLTFLoader.js`'s internal `import * as THREE from 'three'` with zero bundler step. If you touch this, note `GLTFLoader.js`'s one relative import (`../utils/BufferGeometryUtils.js`) was rewritten to the bare specifier `three/addons/utils/BufferGeometryUtils.js` to match an import-map entry — a raw relative import wouldn't resolve correctly once inlined into the page's own module scope.
- `DRACOLoader` still fetches its own decoder files (`draco_decoder.js`, `draco_wasm_wrapper.js`, `draco_decoder.wasm`) via real `fetch()` calls under the hood, same as `<model-viewer>`'s bundled version did — so the same `window.fetch()`-patching trick (see the `LOCAL_ASSETS` map in `site/template.html`) is still needed for exactly those three filenames.
- The model itself no longer needs any fetch-interception trick: `GLTFLoader.parse(arrayBuffer, ...)` takes the decoded model bytes directly, no URL/fetch/blob involved at all. This is simpler than the old `<model-viewer>` setup, which needed a fake sentinel-URL trick just to hand it something URL-shaped.
- A `<script type="module">` is required for any ESM-format code — a classic `<script>` tag fails to parse `export`/`import` syntax silently in a way that looks like nothing loaded at all (zero errors, nothing happens) rather than a clear syntax error.

## Two axis/rotation traps already debugged — don't relearn these

**1. The Z-up mesh vs. Y-up Three.js convention.** The mesh is authored Z-up (x,y horizontal, z=height); Three.js's ecosystem conventionally expects Y-up. Fixed by applying **one** `-90° X` rotation to the loaded model's root `Group` (`modelGroup.rotation.x = -Math.PI/2` in `template.html`), then parenting hotspot markers' *world positions* via `modelGroup.localToWorld(new THREE.Vector3(x,y,z))` using each landmark's raw authored coordinate directly. This avoids the entire class of bug that plagued the old `<model-viewer>` version, where `camera-target` and hotspot `data-position` turned out to need two different, undocumented axis conventions — see git history for that saga if curious; it's not relevant to the current Three.js code at all.

**2. `Object3D.lookAt()`'s camera-specific branch.** Three.js's `lookAt()` has a special case: for objects with `isCamera` (or `isLight`) truthy, it aims the object's **-Z** axis at the target (correct camera behavior); a plain `Object3D` gets the **reversed** convention (+Z at target — meant for billboards/sprites). The landmark fly-to code (`startTweenTo()`) uses a throwaway `Object3D` purely to compute a look-at quaternion via `lookAt()`, and initially got backwards results (camera facing exactly away from the target) until `dummy.isCamera = true` was set before calling `lookAt()`. If you write similar look-at-quaternion helper code anywhere, set this flag.

## Material defaults and collision performance

**trimesh's GLB export doesn't set `metallicFactor`, which defaults to the glTF spec's `1.0` (fully metallic).** A fully metallic `MeshStandardMaterial` barely responds to plain ambient/hemisphere/directional lights with no environment map to reflect — this is why colors looked dull/dark before it was noticed. Fixed by traversing loaded meshes and forcing `material.metalness = 0` (this is a flat-colored relief map, not shiny metal). If colors ever look washed out or dark again, check this first before suspecting a color-space bug — it was tested and ruled out (`THREE.ColorManagement.enabled = false` made no measurable difference; the metalness fix alone took a sampled red hospital-building pixel from `[120,49,45]` to `[204,94,91]` against an intended `[214,39,40]`).

**A plain (non-accelerated) raycast against this disk's ~1.6M faces measured at ~70ms** — far too slow to run every frame for collision detection. `three-mesh-bvh` (vendored in `site/three-mesh-bvh.js`, wired in near the top of the module script by patching `computeBoundsTree`/`disposeBoundsTree` onto `BufferGeometry.prototype` and `acceleratedRaycast` onto `Mesh.prototype.raycast`) brought the same raycast down to ~0.004ms — call `geometry.computeBoundsTree()` on every loaded mesh's geometry once after parsing (already done in the `gltfLoader.parse()` success callback) or raycasts silently fall back to the slow brute-force path. Collision itself (`clampToSurface()` for the ground/roof, plus a forward raycast in `updateMovement()` for walls) was verified with a ray-parity inside/outside test (odd number of raycast hits along an arbitrary direction = camera is embedded in solid geometry), not by comparing displacement distances — Playwright's headless `requestAnimationFrame` throttling made timing-based checks unreliable (the same nominal "hold W" duration produced identical travelled distances regardless of how long the key was actually held, since `dt` is clamped to a 0.1s max per frame in the render loop and headless Chromium doesn't reliably fire rAF at 60fps).

## Debugging approach that actually works here

Visual screenshots alone are not reliable for verifying 3D alignment — small buildings can be a handful of pixels on screen, and color-threshold matching on screenshots produces false positives under directional lighting. What works:

- Serve the built HTML locally (`python3 -m http.server`) and drive it with Playwright.
- `template.html` exposes `window.__debug = { THREE, scene, camera, renderer, modelGroup }` right after scene setup — use this from `page.evaluate()` to read exact camera position/quaternion, run `Box3().setFromObject(...)`, decompose Euler angles, etc., rather than trusting a screenshot. This is how the two axis bugs above were actually found and fixed — by comparing hand-computed expected coordinates against what the page's own live objects reported, not by eyeballing renders.
- If you add a hotspot/camera feature and it "looks kind of right," don't trust it — get the exact numeric check before believing it's correct. This bit us more than once across this project's life (both under `<model-viewer>` and, briefly, under Three.js).

## Data pipeline

Same chain as `macon-3d-print`: `fetch_osm.py -> parse_osm.py -> filter_ms_footprints.py -> merge_footprints.py -> assign_zones.py`, but the terminal step here is `build_colored_disk.py` (not `build_grid.py`'s plain STL export) — it imports `build_grid.py` directly for shared terrain/geometry logic, so keep both together in `scripts/`. Roads in this (web-only, non-printed) version render flush with the terrain rather than grooved (`build_colored_disk.py` only builds a road ribbon for color classification, no boolean cut) — printing constraints don't apply here. Water keeps its physical recess.

Buildings not in one of the four special categories (hospital/government/Mercer/landmark) are colored by their real zoning parcel (`fetch_zoning.py` -> Bibb County's public tax-assessor `Parcel_CAMA2022` FeatureServer, 68,970 parcels with a `ZONINGCODE` field, spatially joined to each building's centroid in `build_colored_disk.py`). Finding the right data source took some digging: the county's "Zoning Information" open-data catalog entry is a Document Link to an interactive Esri Web AppBuilder app (`gis.maconbibb.us/MBPZ518`), not a queryable feature service — its `config.json` points at a webmap on a local Portal-for-ArcGIS instance that needs auth this environment doesn't have. The tax-assessor CAMA parcel layer (hosted separately, publicly, on `services2.arcgis.com`) has the same `ZONINGCODE` info as a plain field with no auth wall, and turned out to be the actually-usable path in — found via the county's DCAT catalog feed (`<hub-name>.hub.arcgis.com/api/feed/dcat-us/1.1.json`, a standard endpoint most ArcGIS Hub sites expose, listing every dataset's REST/CSV/GeoJSON/Shapefile/KML download URLs directly — much faster than digging through the Hub's search UI).

Named place labels (neighborhoods, industrial areas, smaller communities) come from OSM's `place=neighbourhood/hamlet/village/...` nodes and named `landuse=industrial` ways/relations, fetched by `scripts/fetch_places.py` and projected into model space by `scripts/build_labels.py` (reusing `build_grid.py`'s CX/CY/MM_PER_M transform and `terrain_z_mm()`, same as the four hand-curated `LANDMARKS` in `site/assemble.py`). Unlike everything else in the pipeline, this data has nothing to do with the GLB/terrain build — `build_labels.py`'s output (`output/labels.json`) is inlined straight into the page by `site/assemble.py` as `__LABELS_JSON__`, so re-running just those two scripts is enough to update labels without touching the (much slower) geometry pipeline. Rendered as plain non-interactive DOM text (`site/template.html`'s `buildPlaceLabels()`/`updatePlaceLabelPositions()`, mirroring the existing hotspot pattern) rather than baked into the mesh, with a per-tier camera-distance fade (`PLACE_LABEL_TIERS`) so all ~175 labels aren't visible at once — a county-wide view only shows industrial areas, flying closer reveals neighborhoods, and closer still reveals smaller communities.

**Querying Overpass by area *name* is ambiguous for anything but a unique name.** The first attempt at fetching place labels used `area["name"="Bibb County"]["boundary"="administrative"]`, which silently matched *two* counties named Bibb (Georgia's and Alabama's) and returned a mix of real Macon neighborhoods and Alabama towns (Brent, Centreville, West Blocton...) with no error or warning — Overpass just unions every match. Querying by bounding box (read from `county_boundary/bibb_county.geojson`, like every other fetch script already does) instead of by name sidesteps the whole class of bug. If an Overpass result set ever contains place names that don't sound right for the area, suspect a name collision in the area filter before suspecting bad OSM data.

**geopandas `sjoin` gotcha, silent and easy to miss**: joining two GeoDataFrames that both kept their original row indices from a larger parent frame (e.g. two independent `df[df.intersects(clip_shape)]` filters) can silently misalign results if those indices happen to collide — not an error, just wrong matches joined onto the wrong rows. Caught this because a zoning-classification match rate looked implausibly low (~6%, when a same-tile eyeball check with `unary_union(...).contains()` showed it should be ~100%) — `.reset_index(drop=True)` on both sides before `gpd.sjoin`, then joining results back via an explicit position column instead of trusting pandas index alignment a second time, fixed it. If a spatial join's match rate looks suspiciously low despite geometries that clearly do overlap, check this before suspecting the geometry itself.

`data/`, `cache/`, and `output/` are gitignored (large, regenerable) -- except `county_boundary/`, which lives outside `data/` specifically so it's committed: every fetch script derives its bbox from it, not a hardcoded value, so it has to actually exist in a fresh clone.
