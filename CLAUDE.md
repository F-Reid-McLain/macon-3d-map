# CLAUDE.md

Guidance for working in this repo.

## What this project is, and where it's going

An interactive 3D relief map of downtown Macon: a hand-rolled Three.js scene with a free-roam camera (WASD + drag-look + Q/E for altitude), shipped as one self-contained HTML file (see `site/assemble.py`). It shares its data-prep pipeline with the sibling `macon-3d-print` repo (physically-printable STLs), but the two are expected to diverge. This repo previously ran on Google's `<model-viewer>` web component (orbit-only camera — look-at-target + distance + two angles, no way to translate through space), which was a dead end for "drive around the city" and got fully replaced. Next up:

- Eventually covering all of Macon, not just the downtown disk, with better building data (Overture Maps Foundation or Bibb County's own GIS, not just OSM) and toggleable stats overlays (Census ACS or similar).
- Real drivable-car physics — the current free-roam camera has terrain/building collision (see below) but no vehicle body, wheels, or momentum. A WASM physics engine (Rapier or Ammo.js) under Three.js is the natural choice when this happens; WASM is already proven in this project via both the Draco decoder and `three-mesh-bvh`'s accelerated raycasting.
- A full WASM game engine (e.g. Godot) was considered and explicitly rejected for now: its footprint (tens of MB before content) blows past what a self-contained single HTML file can reasonably hold, and it would badly hurt the Playwright-based screenshot/raycast debugging loop this project leans on heavily (see below). Worth revisiting only if this ever moves off the self-contained-single-file model entirely.

## Hard-won constraints — don't relearn these the hard way

**The page must be one self-contained HTML file with zero external network calls.** This was originally driven by publishing to a CSP-locked hosting environment. The exact policy, confirmed directly from a real browser console: `script-src 'self' 'unsafe-inline' 'unsafe-eval' blob:` and `connect-src 'self'` -- note the asymmetry: `blob:` is allowed for **loading a script**, but `fetch()` on a `blob:` URL is still blocked (`connect-src` has no `blob:`), and `data:` is not allowed for scripts at all. These are two different CSP directives governing two different browser mechanisms, and it's easy to fix one and still be blocked by the other. Concretely:

- Three.js core + `GLTFLoader.js` + `DRACOLoader.js` + `BufferGeometryUtils.js` (a cross-dependency `GLTFLoader.js` needs) + `three-mesh-bvh` are vendored as plain files in `site/`, then embedded via an **import map whose entries are `blob:` URLs** (created at runtime via `URL.createObjectURL()` from the same embedded base64 payloads) -- a first attempt used `data:text/javascript;base64,...` URIs directly, which loaded fine with no CSP at all (this project's local `python3 -m http.server` testing) but were silently blocked the moment this shipped to the real CSP-locked platform, since `data:` isn't in `script-src` there. The import map is built and injected by a **synchronous classic `<script>`** (not `type="module"`, no `async`/`defer`) that runs and completes -- with the import map already in the DOM -- before the HTML parser reaches the later `<script type="module">` that actually does `import ... from "three"`; import map registration must happen before any module script needing it is evaluated. If you touch this, note `GLTFLoader.js`'s one relative import (`../utils/BufferGeometryUtils.js`) was rewritten to the bare specifier `three/addons/utils/BufferGeometryUtils.js` to match an import-map entry — a raw relative import wouldn't resolve correctly once inlined into the page's own module scope.
- `DRACOLoader` still fetches its own decoder files (`draco_decoder.js`, `draco_wasm_wrapper.js`, `draco_decoder.wasm`) via real `fetch()` calls under the hood, same as `<model-viewer>`'s bundled version did — so the `window.fetch()`-patching trick (see the `LOCAL_ASSETS` map in `site/template.html`) is still needed for exactly those three filenames, since `connect-src` blocks a real fetch to anything, blob: included.
- The model itself no longer needs any fetch-interception trick: `GLTFLoader.parse(arrayBuffer, ...)` takes the decoded model bytes directly, no URL/fetch/blob involved at all. This is simpler than the old `<model-viewer>` setup, which needed a fake sentinel-URL trick just to hand it something URL-shaped.
- A `<script type="module">` is required for any ESM-format code — a classic `<script>` tag fails to parse `export`/`import` syntax silently in a way that looks like nothing loaded at all (zero errors, nothing happens) rather than a clear syntax error.
- **Test against a server that actually sends the real CSP header, not a bare `python3 -m http.server` with no CSP at all.** The `data:` URI import-map mistake above loaded perfectly in every local Playwright test this session ran, because none of them set any CSP -- the bug only surfaced after publishing to the real platform. `scripts/`-adjacent local testing should send `Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval' blob:; connect-src 'self'; font-src 'self' data:; img-src 'self' data: blob:; worker-src 'self' blob:;` (a `SimpleHTTPRequestHandler` subclass overriding `end_headers()` to add this one header works fine) so a real CSP violation shows up locally instead of only after publishing.

## Two axis/rotation traps already debugged — don't relearn these

**1. The Z-up mesh vs. Y-up Three.js convention.** The mesh is authored Z-up (x,y horizontal, z=height); Three.js's ecosystem conventionally expects Y-up. Fixed by applying **one** `-90° X` rotation to the loaded model's root `Group` (`modelGroup.rotation.x = -Math.PI/2` in `template.html`), then parenting hotspot markers' *world positions* via `modelGroup.localToWorld(new THREE.Vector3(x,y,z))` using each landmark's raw authored coordinate directly. This avoids the entire class of bug that plagued the old `<model-viewer>` version, where `camera-target` and hotspot `data-position` turned out to need two different, undocumented axis conventions — see git history for that saga if curious; it's not relevant to the current Three.js code at all.

**2. `Object3D.lookAt()`'s camera-specific branch.** Three.js's `lookAt()` has a special case: for objects with `isCamera` (or `isLight`) truthy, it aims the object's **-Z** axis at the target (correct camera behavior); a plain `Object3D` gets the **reversed** convention (+Z at target — meant for billboards/sprites). The landmark fly-to code (`startTweenTo()`) uses a throwaway `Object3D` purely to compute a look-at quaternion via `lookAt()`, and initially got backwards results (camera facing exactly away from the target) until `dummy.isCamera = true` was set before calling `lookAt()`. If you write similar look-at-quaternion helper code anywhere, set this flag.

## Material defaults and collision performance

**trimesh's GLB export doesn't set `metallicFactor`, which defaults to the glTF spec's `1.0` (fully metallic).** A fully metallic `MeshStandardMaterial` barely responds to plain ambient/hemisphere/directional lights with no environment map to reflect — this is why colors looked dull/dark before it was noticed. Fixed by traversing loaded meshes and forcing `material.metalness = 0` (this is a flat-colored relief map, not shiny metal). If colors ever look washed out or dark again, check this first before suspecting a color-space bug — it was tested and ruled out (`THREE.ColorManagement.enabled = false` made no measurable difference; the metalness fix alone took a sampled red hospital-building pixel from `[120,49,45]` to `[204,94,91]` against an intended `[214,39,40]`).

**A plain (non-accelerated) raycast against this disk's ~1.6M faces measured at ~70ms** — far too slow to run every frame for collision detection. `three-mesh-bvh` (vendored in `site/three-mesh-bvh.js`, wired in near the top of the module script by patching `computeBoundsTree`/`disposeBoundsTree` onto `BufferGeometry.prototype` and `acceleratedRaycast` onto `Mesh.prototype.raycast`) brought the same raycast down to ~0.004ms — call `geometry.computeBoundsTree()` on every loaded mesh's geometry once after parsing (already done in the `gltfLoader.parse()` success callback) or raycasts silently fall back to the slow brute-force path. Collision itself (`clampToSurface()` for the ground/roof, plus a forward raycast in `updateMovement()` for walls) was verified with a ray-parity inside/outside test (odd number of raycast hits along an arbitrary direction = camera is embedded in solid geometry), not by comparing displacement distances — Playwright's headless `requestAnimationFrame` throttling made timing-based checks unreliable (the same nominal "hold W" duration produced identical travelled distances regardless of how long the key was actually held, since `dt` is clamped to a 0.1s max per frame in the render loop and headless Chromium doesn't reliably fire rAF at 60fps).

## Debugging approach that actually works here

Visual screenshots alone are not reliable for verifying 3D alignment — small buildings can be a handful of pixels on screen, and color-threshold matching on screenshots produces false positives under directional lighting. What works:

- Serve the built HTML locally (`python3 -m http.server`) and drive it with Playwright.
- `template.html` exposes `window.__debug = { THREE, scene, camera, renderer, modelGroup }` right after scene setup — use this from `page.evaluate()` to read exact camera position/quaternion, run `Box3().setFromObject(...)`, decompose Euler angles, etc., rather than trusting a screenshot. This is how the two axis bugs above were actually found and fixed — by comparing hand-computed expected coordinates against what the page's own live objects reported, not by eyeballing renders.
- If you add a hotspot/camera feature and it "looks kind of right," don't trust it — get the exact numeric check before believing it's correct. This bit us more than once across this project's life (both under `<model-viewer>` and, briefly, under Three.js).

## Data pipeline

Same chain as `macon-3d-print`: `fetch_osm.py -> parse_osm.py -> filter_ms_footprints.py -> merge_footprints.py -> assign_zones.py`, but the terminal step here is `build_colored_disk.py` (not `build_grid.py`'s plain STL export) — it imports `build_grid.py` directly for shared terrain/geometry logic, so keep both together in `scripts/`. Roads in this (web-only, non-printed) version render flush with the terrain rather than grooved (`build_colored_disk.py` only builds a road ribbon for color classification, no boolean cut) — printing constraints don't apply here. Water keeps its physical recess.

Buildings not in one of the four special categories (hospital/government/Mercer/landmark) are colored by their real zoning parcel (`fetch_zoning.py` -> Bibb County's public tax-assessor `Parcel_CAMA2022` FeatureServer, 68,970 parcels with a `ZONINGCODE` field, spatially joined to each building's centroid in `build_colored_disk.py`). Finding the right data source took some digging: the county's "Zoning Information" open-data catalog entry is a Document Link to an interactive Esri Web AppBuilder app (`gis.maconbibb.us/MBPZ518`), not a queryable feature service — its `config.json` points at a webmap on a local Portal-for-ArcGIS instance that needs auth this environment doesn't have. The tax-assessor CAMA parcel layer (hosted separately, publicly, on `services2.arcgis.com`) has the same `ZONINGCODE` info as a plain field with no auth wall, and turned out to be the actually-usable path in — found via the county's DCAT catalog feed (`<hub-name>.hub.arcgis.com/api/feed/dcat-us/1.1.json`, a standard endpoint most ArcGIS Hub sites expose, listing every dataset's REST/CSV/GeoJSON/Shapefile/KML download URLs directly — much faster than digging through the Hub's search UI).

Named place labels (neighborhoods, industrial areas, smaller communities) come from OSM's `place=neighbourhood/hamlet/village/...` nodes and named `landuse=industrial` ways/relations, fetched by `scripts/fetch_places.py` and projected into model space by `scripts/build_labels.py` (reusing `build_grid.py`'s CX/CY/MM_PER_M transform and `terrain_z_mm()`, same as the hand-curated `LANDMARKS` in `site/assemble.py`). Unlike everything else in the pipeline, this data has nothing to do with the GLB/terrain build — `build_labels.py`'s output (`output/labels.json`) is inlined straight into the page by `site/assemble.py` as `__LABELS_JSON__`, so re-running just those two scripts is enough to update labels without touching the (much slower) geometry pipeline. Rendered as plain non-interactive DOM text (`site/template.html`'s `buildPlaceLabels()`/`updatePlaceLabelPositions()`, mirroring the existing hotspot pattern) rather than baked into the mesh, with a per-tier camera-distance fade (`PLACE_LABEL_TIERS`) so all ~175 labels aren't visible at once — a county-wide view only shows industrial areas, flying closer reveals neighborhoods, and closer still reveals smaller communities.

A fourth label tier, "highway" (I-75, US 41, ...), needs no new data fetch — `build_labels.py`'s `build_highway_labels()` reads the same `bg.roads_all` GeoDataFrame the base-map road geometry uses, filtered to motorway/trunk/primary with a `ref` or `name` tag (`ref` added to `parse_osm.py`'s road parsing since it wasn't kept before). Real highways are split into dozens of short OSM ways sharing one name/ref, so segments are grouped by route and stitched back into as-long-as-possible lines with `shapely.ops.linemerge` before placing a label every ~4000m along each merged line (capped per line, since divided highways are mapped as two separate parallel carriageways in OSM and roughly double the naive label count) — labeling every raw segment individually would have produced dozens of duplicate labels stacked on top of each other. Rendered with a distinct shield/badge CSS class (`site/template.html`'s `.place-label.tier-highway`) and visible from farther away than any other tier, matching how real maps keep route shields legible at a zoomed-out view. **Gotcha**: `shapely.ops.linemerge()` throws `ValueError: Cannot linemerge <LineString>` if `unary_union()` on a route with only one matching way collapses down to a plain `LineString` instead of a `MultiLineString` — `linemerge` expects the latter. Only call it when the union result actually is a `MultiLineString`; otherwise use the union result directly.

A fifth label tier, "water", labels real named rivers/lakes (`build_labels.py`'s `build_water_labels()`). `parse_osm.py`'s water section originally dropped the OSM `name` tag entirely (only `kind`/`geometry` were kept, since the only prior consumer, `build_grid.py`'s terrain-recess cutting, never needed a name) — fixed to keep it, then re-ran `parse_osm.py` against the already-cached `data/osm_raw.json` (no new Overpass fetch needed) to regenerate `data/water_raw.geojson` with names. Rivers get the same linemerge-and-space-out treatment as highways; lakes/ponds get one label at their unioned-by-name centroid, filtered to `WATER_AREA_MIN_M2` (50,000 m²) to exclude the many small private ponds in the raw data (e.g. "Kraftsman Association Lake") that aren't real geographic landmarks.

The industrial place-label tier originally included every named `landuse=industrial`/`commercial` OSM way regardless of what it actually was, which meant scattered gas-pipeline infrastructure (Southern Natural Gas, Atlanta Gas & Light, Colonial Pipeline compressor/metering sites, all tagged `pipeline=substation`) dominated the tier alongside real employers. Filtering on `tags.get("pipeline") != "substation"` in `build_labels.py`'s `build()` cleanly separates the two (verified against the raw data: 14 substation-tagged entries excluded, 13 real facilities like Kumho Tire and Riverwood International kept) without any name-pattern guessing.

**Three more label fixes, all aimed at overlabeling/misalignment complaints.** (1) `highway_label_text()` used to fall back to the OSM `name` tag when a `highway=primary` way had no numbered `ref`, which meant ordinary streets (Sardis Church Road, Mulberry Street) got the same shield-badge treatment as I-75/US 41 -- looked wrong and cluttered the tier with roads nobody would call a highway. Now returns `None` (no label at all) when there's no real route number. (2) Divided highways and multi-channel rivers are mapped in OSM as separate parallel ways sharing one name, and each parallel way got its own repeated label -- for a road/river only a few dozen meters wide at a point, that produced two near-identical labels stacked directly on top of each other. `dedupe_close_labels()` (called once on the fully-assembled list in `build()`) collapses same-tier, same-name labels within `DEDUPE_MIN_DIST_M` (150m) down to one. (3) Neighbourhood/hamlet OSM nodes have essentially no `population` tag (1 of 202) to judge real size by, so `buildings_nearby()` counts real building footprints (`bg.buildings_all`, via an `STRtree`) within `PLACE_DENSITY_RADIUS_M` (250m) as a real-data proxy instead -- a handful of named points sit in fields with zero buildings anywhere near them (likely a crossroads name or a stray node), and `PLACE_MIN_BUILDINGS_NEARBY` (15, picked as roughly the county-wide 10th percentile) drops those and the next-sparsest tier without gutting the legitimately-small hamlet tier. Together these took total place-label count from 276 to 247, mostly from tightening rather than an aggressive prune.

The hand-curated `LANDMARKS` array in `site/assemble.py` grew from the original 4 categories (hospital/government/mercer/landmark) to 8: `medical` (renamed from `hospital` — the single original hospital plus 6 more hospitals/clinics found via a targeted Overpass query for `amenity=hospital`/`healthcare=hospital`/`amenity=clinic`, since the main county-wide OSM fetch never targeted standalone medical POI nodes), `heritage` (Ocmulgee Mounds National Historical Park — a marker only, since reconstructing real mound earthwork geometry isn't possible at this model's terrain resolution without fabricating detail), `music` (Little Richard's childhood home, the Otis Redding Foundation, Mercer Music at Capricorn, The Big House, Rose Hill Cemetery, the Douglass Theatre), `church`, and `buildings` (renamed conceptually from the old catch-all `landmark`, which still exists as a smaller "other" bucket). Coordinates for the new entries came from a mix of direct Overpass name lookups (`nwr["name"~"...",i]` regex queries against the county bbox) and, where OSM didn't have the feature, Nominatim-geocoded street addresses sourced via web search — all converted to model space with the same `to_model_xyz()` helper `build_labels.py` already uses, not hand-guessed. **Gotcha**: the building-color legend rows (`LEGEND_SECTIONS` in `site/template.html`, a *different* system — GLB mesh nodes from `build_colored_disk.py`'s `CATEGORIES`, unrelated to the `LANDMARKS` hotspot array) still use the literal string `"hospital"` for their node name and `countId`/`count-hospital` DOM id, since that's the GLB mesh's own category name and wasn't renamed. `buildHotspots()`'s per-legend-row count injection (`site/template.html`) has to map `"hospital"` → the `LANDMARKS` category `"medical"` explicitly (`countIdToCategory`) to keep that count correct now that the two names have diverged.

**Airport pavement (runways/taxiways/aprons) needed a real new fetch, not just a re-parse.** `fetch_osm.py`'s original Overpass query never requested `aeroway=*` at all -- hangars happened to already render (they're separately tagged `building=yes`/`building=hangar`, caught by the ordinary building fetch), but the actual runway/taxiway/apron pavement wasn't in `data/osm_raw.json` in any form. Rather than re-running the full county-wide fetch (hundreds of thousands of elements, slow), ran one small targeted Overpass query for `way["aeroway"]`/`relation["aeroway"]` in the same county bbox, then merged its elements into the existing cached `data/osm_raw.json` by `(type, id)` (1365 of 1577 fetched elements were genuinely new; the rest were nodes/ways already present from the building/road fetch) -- `fetch_osm.py`'s own QUERY was also updated to include the `aeroway` clause, so a future from-scratch re-fetch stays in sync with what's actually cached instead of silently regressing. `parse_osm.py` gained a new aeroway section writing `data/aeroway_raw.geojson`, with a `kind` column (`runway_area`/`runway_line`/`taxiway`/`apron`) distinguishing real closed-ring polygons from bare centerlines -- about a third of runways and nearly all taxiways in the real OSM data here are just a centerline with no width tag, buffered to a fixed realistic width (`RUNWAY_WIDTH_M`=45, `TAXIWAY_WIDTH_M`=15 in `build_colored_disk.py`) rather than left as an invisible zero-width line. Rendered with the same terrain-draping decal approach as roads (`drape_polygon_mesh`, `ROAD_DECAL_LIFT_MM`), as three new toggleable `CATEGORIES`/`LEGEND_SECTIONS` entries (`runway`/`taxiway`/`apron`) -- aprons specifically called out in the legend as the real-world equivalent of a "parking lot" for aircraft, distinct from the ordinary car-parking `parking` category which already covered the airport's actual car parking lots.

**All 52 `LANDMARKS` hotspots were floating at bare terrain height, not rooftop height -- a textbook case of the "looks kind of right" trap this file already warns about.** Both the original 26 (`build_grid.py`'s `terrain_z_mm()`, per the water-labels entry above) and this session's 26 new ones (`build_labels.py`'s `to_model_xyz()`, same terrain-only function) used ground-level z with a few mm of float, never the actual building's height. From directly above this looked fine; from any oblique angle, a marker sitting several mm below a building's real roof visibly drifts off the building as the camera orbits -- exactly the "not centered on the buildings, changes with the angle viewed" symptom, and an unavoidable consequence of an inaccurate z, not a bug in the projection math (`updateHotspotScreenPositions()`'s `worldPos.project(camera)` is exact). Fixed with a one-off correction pass (not saved as a script, just run once): for each landmark, look up its real building footprint in `data/buildings_raw.geojson` -- first by exact/substring name match, falling back to the closest building centroid within 60m if no name matches -- and replace x/y with that building's true centroid and z with `terrain_z_mm() + height_m * METERS_TO_MM + 4mm` (float above the *rooftop*, not the ground; same convention as `LABEL_FLOAT_MM`). Deliberately closest-centroid, not largest-building, for the fallback: picking the biggest nearby building would bias toward snapping a small unnamed clinic onto an adjacent much bigger hospital block just because it has more floor area. 3 of 52 (Ocmulgee Mounds, Rose Hill Cemetery, Piedmont Macon North Hospital) had no real building to snap to and correctly stayed at terrain height -- two are landscape features with no building at all, not a matching failure.

**Free-roam movement speed was a flat 220mm/sec regardless of camera altitude -- fine at the county-wide default view, wildly too fast zoomed in close to a single building** (often well under 1mm tall at this scale, crossed in a fraction of a second). Fixed by scaling `MOVE_SPEED` by the camera's current height above whatever's directly below it (`groundAltitude`, tracked once per frame off the same downward raycast `clampToSurface()` already does -- no extra raycast needed), full speed at/above `SPEED_REFERENCE_ALTITUDE_MM` (250mm, roughly the default view's height) down to a `MIN_SPEED_SCALE` floor (5%) so it's slow, not frozen, right up against a surface.

**A dedicated "🔍 Search" button sits right under the "☰ Index" panel toggle, always reachable even with the panel collapsed** -- clicking it expands the panel (if collapsed) and focuses the map-search box directly, so finding a place doesn't require first hunting through an opened panel for the field. `panel`/`panelToggle`/the new `mapSearchToggle` button's collapsed state has to stay in sync across three DOM elements at three call sites (the Index toggle's click handler, this button's own click handler, and the touch-device initial-collapsed-on-load block) -- consolidated into one `setPanelCollapsed(collapsed)` setter instead of three places each separately remembering to update all three classes/the aria attribute, which is exactly the kind of thing that quietly drifts when a fourth touch point gets added later. Verified via jsdom (see below) that clicking the search button while collapsed expands + focuses, clicking it while already expanded just re-focuses without re-collapsing, and the Index toggle still round-trips correctly afterward.

**Two search boxes: settings search (filters the legend) and map/POI search (flies the camera to a named place).** Both are plain `<input type="search">` elements, deliberately unrelated implementations rather than one generalized "search" abstraction -- they search fundamentally different things (already-rendered DOM rows vs. a flat data index) and do different things with a match (show/hide vs. fly-to), so sharing code between them would mean more indirection for no real reuse. `wireLegendSearch()` reads the DOM `buildLegend()` already built (row `.legend-label` text, section `.legend-section-master .desc` heading text) rather than re-deriving anything from `LEGEND_SECTIONS`, so it can't drift out of sync with what's actually rendered -- a heading match shows every row in that section (not just rows whose own label also happens to match), and a match force-expands a collapsed overlay section to surface it. **Restoring state on clear is snapshotted at the START of each search, not once at page load** -- if the search just reset every section back to its `collapsedByDefault` state, it would silently undo any manual expand/collapse the user had done themselves before typing anything; `collapsedSnapshot` (a `Map` of section element -> was-it-collapsed, captured on the empty -> non-empty transition, discarded on the next non-empty -> empty one) fixes this. `buildMapSearch()` builds one flat `MAP_SEARCH_INDEX` from `LANDMARKS` + `LABELS` combined (both are just "a named thing with an x/y/z" from search's point of view, despite being rendered completely differently -- fixed hotspot dots vs. floating camera-distance-faded text) once at load, live-filters into a results dropdown as you type (startsWith-matches ranked above contains-elsewhere, capped at `MAP_SEARCH_MAX_RESULTS`=20), and reuses the *existing* fly-to machinery for both kinds of result: `focusOn()` for landmarks (already existed, pulses the hotspot dot + sidebar entry) and a new `flyToLabel()` for place labels (same tween, but pulses the label's own text via a new `.place-label.pulsing` CSS state -- there's no sidebar entry to mark active for ~250 place labels the way there is for landmarks, so the label just needs its own DOM `id="lbl-"+lb.id`, added in `buildPlaceLabels()`, to be targetable at all). **A real, easy-to-miss regression these two boxes introduced**: the WASD/QE movement keydown listener is on `window` and previously added *every* keydown's `e.code` to the movement `keys` Set unconditionally -- typing "redlining" into either search box would have also registered as W/A/S/D/E movement input and sent the camera flying while the user tried to type. Fixed with an `isTypingTarget(el)` guard on keyDOWN only (checks `e.target.tagName` for INPUT/TEXTAREA) -- keyUP is deliberately left unguarded, since a movement key released after focus has already moved to the search box (e.g. still holding "W" when clicking into it) must still clear from `keys` or it gets stuck "held" forever; removing a key that was never added is a harmless no-op either way. **Verified functionally, not just syntax-checked**: no WebGL/browser available in this environment, but `wireLegendSearch()`/`buildMapSearch()`/the typing guard don't touch Three.js at all, so each was extracted from the built HTML and exercised against a real DOM via `jsdom` (installed ad hoc, not a project dependency) in a throwaway scratchpad script -- 18 assertions covering filtering, heading-vs-row matching, the collapse-state-snapshot edge case, startsWith ranking, click/Enter/Escape handling, the result cap, and the keydown/keyup guard, all passing, before trusting any of it.

**Legend reorganized into 9 always-headed sections, each with a select-all/none master toggle.** The old top group (hospital/government/mercer/landmark) was the only headerless section -- fine at 4 rows, but reads as visually inconsistent once there are 9 sections to scan past, so it got a real heading ("Special-cased buildings") like everything else. "Other features" (7 unrelated rows -- roads, parking, water, 3 airport categories, terrain) got split into "Infrastructure" (road/parking/water), "Airport" (runway/taxiway/apron), and "Terrain" (terrain + the true-to-scale sub-option) -- both a clarity win and what makes a *section*-level master toggle actually mean something specific ("hide the whole airport layer" vs. an arbitrary grab-bag). The master toggle is a real tri-state checkbox (`indeterminate` when a section's rows are a mix of shown/hidden, same square-switch styling with the dot parked at the track's midpoint) built alongside each section's row loop in `buildLegend()`: every real mesh-backed checkbox built in that iteration pushes into a local `sectionCheckboxes` array, an `updateMasterState()` closure recomputes the master's checked/indeterminate state whenever any of them changes, and the master's own change handler flips every one of them to match (dispatching a real `"change"` event on each, so it reuses each row's existing visibility-toggle logic rather than duplicating it). Deliberately excludes `scaleToggle`/`noToggle`/disabled ("nothing in this category") rows from that array -- a "select all" control should only ever touch actual layer-visibility checkboxes. Sections with fewer than 2 real toggleable rows (just "Terrain," which has 1) skip rendering a master entirely -- redundant with the single row beneath it otherwise. **Gotcha avoided, not hit**: the master checkbox can't live inside the same clickable element as the section's expand/collapse control, since nesting an `<input>` inside a `<button>` is invalid HTML and would make every checkbox click also fire the collapse toggle -- restructured the heading into a `<div>` containing a separate `<label>` (master toggle) and `<button>` (chevron/collapse), two independent interactive elements instead of one overloaded one.

**Terrain can now be hidden, and a "true-to-scale elevation" toggle exists, both purely client-side (no GLB rebuild).** Terrain's legend row lost its `noToggle: true` and now behaves exactly like every other category (this is a deliberately multi-purpose tool -- letting the user emphasize/de-emphasize any layer, including the ground plane itself, was the explicit ask; the original "there's not much point in a relief map with no ground" reasoning was about the *default* view, not a hard constraint). The true-to-scale toggle is a fundamentally different kind of control -- not a per-category mesh visibility flag but a scene-wide transform (`setTrueScaleElevation()`), so it's a new `scaleToggle: true` row type in `LEGEND_SECTIONS`/`buildLegend()` rather than reusing the `node`-based mesh-lookup path. It sets `modelGroup.scale.z` (applied to children *before* the group's own `-90deg` X rotation, i.e. this is the raw mesh's authored Z/"height" axis, the same one that rotation maps to world "up") to `0.4` = `MM_PER_M / TERRAIN_MM_PER_M` from `build_grid.py`, undoing exactly the 2.5x terrain exaggeration. Pivots for free at `z=0` with no extra math, because that's exactly where the terrain plate's own physical underside already sits (`build_terrain_base()`'s bottom face is literally `z=0`) -- the ground's bottom face never shifts, relief just compresses toward it. Everything draped flush on terrain (roads/water/parking/aeroway/overlay decals, all built from `terrain_z_mm()` plus a small fixed lift) scales correctly right along with it, and hotspot/label positions (computed via `modelGroup.localToWorld()`, which respects the group's current scale automatically) and camera collision (raycasts against `modelGroup`'s actual world-transformed geometry) both just work with zero extra code. **Known inexactness, documented in the row's own info text rather than hidden**: buildings use a *separate*, larger exaggeration factor (`METERS_TO_MM=0.3mm/m` vs terrain's `TERRAIN_MM_PER_M=0.2mm/m`, against a true `MM_PER_M=0.08mm/m`) that this one flat scale can't independently retarget -- their height also shrinks by the same 0.4x as a side effect, bringing them from 3.75x-exaggerated down to 1.5x-exaggerated, not all the way to fully true-to-scale on their own. Doing that exactly would need a second baked GLB variant (this model has no way to recover "how much of this baked vertex's height was exaggerated terrain vs. real building height" at runtime from one exported mesh) -- judged not worth the doubled asset size for what the terrain-focused ask actually needed.

**Querying Overpass by area *name* is ambiguous for anything but a unique name.** The first attempt at fetching place labels used `area["name"="Bibb County"]["boundary"="administrative"]`, which silently matched *two* counties named Bibb (Georgia's and Alabama's) and returned a mix of real Macon neighborhoods and Alabama towns (Brent, Centreville, West Blocton...) with no error or warning — Overpass just unions every match. Querying by bounding box (read from `county_boundary/bibb_county.geojson`, like every other fetch script already does) instead of by name sidesteps the whole class of bug. If an Overpass result set ever contains place names that don't sound right for the area, suspect a name collision in the area filter before suspecting bad OSM data.

**geopandas `sjoin` gotcha, silent and easy to miss**: joining two GeoDataFrames that both kept their original row indices from a larger parent frame (e.g. two independent `df[df.intersects(clip_shape)]` filters) can silently misalign results if those indices happen to collide — not an error, just wrong matches joined onto the wrong rows. Caught this because a zoning-classification match rate looked implausibly low (~6%, when a same-tile eyeball check with `unary_union(...).contains()` showed it should be ~100%) — `.reset_index(drop=True)` on both sides before `gpd.sjoin`, then joining results back via an explicit position column instead of trusting pandas index alignment a second time, fixed it. If a spatial join's match rate looks suspiciously low despite geometries that clearly do overlap, check this before suspecting the geometry itself.

`data/`, `cache/`, and `output/` are gitignored (large, regenerable) -- except `county_boundary/`, which lives outside `data/` specifically so it's committed: every fetch script derives its bbox from it, not a hardcoded value, so it has to actually exist in a fresh clone.

## Hosting: GitHub Pages, unlisted

The repo is public, but Pages is deployed as an intentionally *unlisted* link, not an announced one -- `index.html` at the repo root is `noindex, nofollow` and nothing links to it. `index.html` is a tiny redirect (see below, now also a device-detection dispatcher) rather than a copy of the real page, specifically to avoid duplicating a many-MB committed file just to satisfy Pages' default `index.html` expectation. `.nojekyll` at the root skips GitHub's default Jekyll processing, which this static single-file site doesn't need and which has its own filename-processing rules that aren't relevant here. Pages was enabled via `gh api repos/.../pages -X POST -f "source[branch]=main" -f "source[path]=/"` rather than the web UI. GitHub Pages does **not** set a CSP by default -- notably more permissive than the "real hosting platform" referenced elsewhere in this file, so the CSP hardening already done there is more than sufficient here, not a gap to fill.

## Mobile: touch controls, and a separate lower-memory build

Movement was keyboard-only (WASD/Q/E/shift) with no touch equivalent, so a phone could look around (drag already used Pointer Events, which fire for touch too) but never actually move -- the biggest mobile gap by far. Fixed with an on-screen joystick (`#touch-joystick`, bottom-left) and small altitude buttons, shown only on coarse-pointer devices via `@media (pointer: coarse)` so desktop is untouched. The joystick uses **magnitude-based speed** (push to the edge to run) instead of a separate boost button/toggle -- deliberately mirrors mobile FPS game conventions. Pinch-to-zoom (two fingers on the canvas) drives the same forward/back dolly the desktop scroll-wheel already does.

**Look-drag needed pointerId-based tracking, not a boolean flag, once a joystick could be active at the same time.** The original code just set `dragging = true` on any canvas `pointerdown` and read every subsequent `pointermove` regardless of which finger it came from -- fine with a mouse (one pointer, ever), broken the moment a second finger (the joystick, or just an incidental second touch) could be down simultaneously, since its pointermove events would get misread as look-drag input. Fixed by tracking one specific `pointerId` per gesture (`dragPointerId` for look, a `Map` of `activePointers` for detecting a pinch), and ignoring pointer events from any other id. `setPointerCapture()` calls are wrapped in `try/catch` -- confirmed via testing that a failed capture (some browser/OS combos throw) must not abort the rest of the handler, or the whole touch loses tracking silently.

**A real device (iPhone, Safari) crashed and reloaded repeatedly loading the full desktop model** -- "A problem repeatedly occurred," Safari's actual wording for a page whose renderer process keeps dying and relaunching, consistent with exceeding iOS's per-tab memory ceiling. Confirmed via Safari's Web Inspector connected to the live device (Mac: Safari → Develop menu → [device] → [tab]) -- the only console output was an unrelated cosmetic `sourceMappingURL` resolution error from a vendored library's dead source-map reference (harmless, only ever fetched by an attached inspector, since removed), which mattered diagnostically: a real OOM kill happens at the OS/WebKit-process level below JavaScript entirely, so it produces **no** console output at all -- the absence of any other error was itself consistent with, not contrary to, the memory theory. Playwright's WebKit engine (same browser family, run on this Mac's own RAM) loaded the page with zero errors, which only rules out fundamental code/architecture bugs (e.g. import map support) -- it can't reproduce a phone-class memory ceiling, since it isn't running on phone-class hardware.

Rather than reduce quality for every visitor, `scripts/build_mobile.sh` builds a **second, separate** lower-geometry variant (`site/downtown_macon_3d_mobile.html`) -- desktop keeps full detail. `DEM_SAMPLE_SPACING_M` (`build_grid.py`) and the output GLB/HTML paths (`build_colored_disk.py`'s `OUTPUT_GLB_PATH`, `site/assemble.py`'s `MODEL_GLB_PATH`/`OUTPUT_HTML_PATH`) are now env-var-overridable specifically so the same pipeline code can produce both variants without duplication. Terrain is by far the dominant cost (7.03M of ~9.6M total faces in the desktop build), so it's the only lever pulled so far: doubling the spacing from the desktop's 20m to 40m cut terrain to 1.9M faces and the total to ~4.47M (~53% overall), with no obvious visual quality loss at normal viewing distance in testing. Going coarser is the *safe* direction -- the opposite of the 10m experiment elsewhere in this file that broke Draco's encoder outright, so this doesn't risk that failure mode. **What looked like round 1 not being enough turned out to be a routing bug, not a capacity problem.** Real A/B evidence from two actual devices on the same round-1 build initially looked conclusive: an iPhone 13 (4GB RAM) crashed repeatedly, an iPhone 15 (6GB RAM) loaded the identical build fine. That led to a round 2 (`SKIP_DEMOGRAPHICS_OVERLAY=1` dropping those overlay nodes entirely -- confirmed hidden geometry, `mesh.visible = false`, stays fully GPU-resident regardless, so they cost ~582K faces for zero benefit on first load; plus terrain spacing 40m -> 60m; combined total ~4.47M -> ~2.94M faces). But the iPhone 13's actual failure turned out to be `index.html`'s fallback link sending it straight to the **desktop** build regardless of device (a separate bug, since fixed -- the visible "click here" text had a hardcoded desktop href, only the automatic redirect was device-aware) -- confirmed by matching the exact byte size of the model it had loaded (4.63MB) to the desktop GLB, not the mobile one. Once that routing bug was fixed, the ORIGINAL round-1 build (40m spacing, demographics included) loaded fine on the same iPhone 13. Round 2's extra cuts were reverted back to round 1 in `scripts/build_mobile.sh` as a result -- they were solving a problem that the evidence in hand no longer supported once the real cause was found. If real device testing turns up an actual memory-ceiling crash again on the correctly-routed round-1 build, redo round 2 (`git log scripts/build_mobile.sh` has the exact settings) rather than guessing at new ones.

**Reverting to round 1 surfaced a real, smaller bug in the road-drape lift margin**: `ROAD_DECAL_LIFT_MM` (see the road-drape section above) was a fixed 0.45mm, calibrated by measurement only against the desktop's 20m terrain grid. Re-measuring the same way (raycast thousands of road vertices against the rendered terrain) at the mobile build's 40m grid found a real, if much smaller, regression -- 0.125% of sampled points below terrain, worst case -0.14mm (vs. the original bug's 21%/-0.32mm). The interpolation-mismatch magnitude that necessitates this lift grows with grid coarseness, so a fixed constant tuned for one resolution will always eventually go stale at another. Measuring the TRUE deviation (subtracting out the lift already applied) at both resolutions -- -0.35mm at 20m, -0.59mm at 40m -- showed the relationship is roughly *linear* in this specific DEM, not the quadratic a naive "twist term scales with cell area" argument would predict. `ROAD_DECAL_LIFT_MM` is now `0.45 * (bg.DEM_SAMPLE_SPACING_M / 20.0)` instead of a bare constant, so it self-scales for whatever resolution a given build actually uses (exactly 0.45 at the desktop's 20m, so this changed nothing there) rather than needing its own re-measurement -- and likely re-discovery as a bug -- every time a build's terrain resolution changes.

`index.html` now does device detection, not just a redirect: `window.matchMedia("(pointer: coarse)")` picks which of the two built HTML files to send a visitor to. No `<meta refresh>` fallback (that can't be conditional) -- a JS-disabled visitor falls back to the visible link, which points at the desktop build; an acceptable edge case next to needing JS to detect touch at all.

## Legend toggles: the model is a multi-node Scene, not one mesh

`build_colored_disk.py` exports a `trimesh.Scene()` with one named node per legend category (`CATEGORIES` list, e.g. `"hospital"`, `"residential"`, `"road"`, `"terrain"`) instead of one big concatenated mesh — `site/template.html` matches meshes by these exact names (`obj.name` after `GLTFLoader.parse()`) to wire up the legend's per-category checkboxes, which just flip `mesh.visible`. If you add a new category, it must appear in **both** `CATEGORIES` (Python) and `LEGEND_SECTIONS` (JS) with matching node names, or the legend row silently shows as disabled/greyed-out (`categoryMeshes` has no entry for it) rather than erroring.

**Per-row documentation and collapsible sections.** With 31 legend rows once every overlay is counted, two usability problems showed up: (1) each row only had a shared per-*section* `note` to explain it — fine when a section was 4 redlining grades, not great when it's 5 occupation categories each needing its own explanation of exactly which Census table/variable it comes from; (2) an always-fully-expanded flat list buried the base-map categories under a wall of overlay rows. Fixed with two independent additions to `LEGEND_SECTIONS`: a per-row `info` field (an array of paragraph strings) rendered in a generic, reusable `#info-modal` opened by a small (i) button on every row (`buildLegend()`'s `infoBtnHtml()`/`wireInfoBtn()`), and a per-*section* `collapsedByDefault` flag that starts the four data-overlay sections (redlining/demographics/occupation/commuting) collapsed while leaving the base-map sections open, exactly as before. Sections without a `heading` (the top hospital/government/mercer/landmark group) stay flat and non-collapsible, unchanged.

Buildings split into named nodes trivially (each is already a separate extruded polygon before concatenation — just group by category before merging instead of merging everything together). Roads/water/parking are NOT naturally separable this way: they used to be colored by testing each terrain triangle's centroid against the road/water/parking polygons (spatial classification), baking all three into one continuous terrain-colored blob with no way to toggle just "roads". Replaced with **decals**: terrain is now uniformly green, and roads/water/parking are each a thin (~0.12mm) colored prism extruded directly from their own polygon, lifted ~0.03mm above the terrain surface (or, for water, resting at the bottom of its recess) so there's no z-fighting. This is also just a better-looking result on its own, not only a toggle feature — roads render as continuous clean ribbons following the real street shape instead of a coarse terrain-grid-resolution-limited approximation.

**Road decals must be unioned before extruding, not extruded per-segment.** A first pass extruded each individual road line's buffered ribbon separately and measured 1.08M faces for just 3 tiles' worth of roads — more than the entire terrain mesh for the same area — because adjacent/crossing streets' ribbons overlap heavily at every intersection, and each tiny segment pays the fixed top+bottom+wall-triangle cost of its own `extrude_polygon()` call. Unioning all ribbons in UTM space first cuts this dramatically before extruding.

**Road decals must be DRAPED per-vertex onto real terrain height, not extruded flat at one sampled height.** The first working version of the above sampled terrain height ONCE per disjoint unioned cluster (its own centroid) and extruded the whole cluster as one flat prism at that height — this floated above dips / clipped through rises wherever a cluster spanned more elevation change than that one sample captured, very visible on Macon's real river bluff, and read as roads "floating" over the map or not connecting where two differently-flat clusters met. Fixed by `drape_polygon_mesh()`: triangulate the (still-unioned, for face-count efficiency) shape via `trimesh.creation.triangulate_polygon`, then sample terrain height **per vertex** (`build_grid.py`'s `terrain_z_mm_batch`, a vectorized batch version of `terrain_z_mm`) instead of once for the whole shape. Because height comes from the same continuous terrain function at each vertex's real (x,y), separately-draped shapes that share a boundary point land on the identical height there too — no seam between them, without needing to actually be one merged mesh. This also fixed the earlier "chunky" look: `ROAD_WIDTH_M` tiers width by real OSM road class instead of one flat 37.5-real-meter value for every road, and the buffer uses `cap_style="flat", join_style="mitre"` instead of shapely's default round join, which was tessellating a fat circular bulge at every bend.

**The drape still needed a bigger, separately-measured lift margin than other decals.** Even with per-vertex draping, roads clipped under terrain "sometimes" — measured directly (sampled 4000 road vertices, raycast straight down against the rendered terrain mesh from Playwright) rather than guessed at: the shared `DECAL_LIFT_MM` (0.03mm) left ~21% of the road network below the terrain surface, down to -0.32mm at the worst points. Root cause is a real, small mismatch, not a bug in the drape logic — the terrain MESH is a triangulated grid (each DEM cell split by one diagonal into two flat triangles), but `terrain_z_mm_batch` samples true bilinear interpolation, and those two don't exactly agree at sub-cell precision. Roads got their own `ROAD_DECAL_LIFT_MM` (0.45mm) instead of bumping the shared constant water/parking also use (those aren't reported as broken and work differently — water sits recessed, parking's footprints are small enough that one centroid sample rarely spans much elevation change). Re-measuring the same way after the fix: 0 of 4000 sampled points below terrain, minimum clearance +0.2mm. If a future decal-on-terrain feature shows intermittent "sometimes" floating/clipping that doesn't fully resolve with an obvious geometry fix, suspect this same sub-cell interpolation mismatch before assuming the geometry logic itself is wrong — measure it the same way (sample vertices, raycast against the terrain mesh) rather than guessing at a lift value.

## A pre-existing place-label bug this session found and fixed

`output/labels.json` (built by `build_labels.py`) can only produce three tiers (`neighbourhood`/`hamlet`/`industrial` -- see `TIER_BY_PLACE_TAG` and the `landuse` fallback in that script). A `labels.json` copied in from another machine/session had a **fourth** tier, `"highway"` (90 of 265 labels, from some earlier/uncommitted iteration of the label-building script), which doesn't exist in `site/template.html`'s `PLACE_LABEL_TIERS` map. Every frame's `updatePlaceLabelPositions()` call threw `Cannot read properties of undefined (reading 'fadeStart')` on the first highway-tiered label it hit, silently aborting *before* `renderer.render()` ever ran that frame -- the visible symptom was a fully black, frozen viewport with only the (independently-updating) hotspot/label DOM overlays still moving, no console output unless you were actually watching for `pageerror` events. If the scene ever seems to freeze/go black again after a UI or camera change, regenerate `output/labels.json` fresh from the *current* `build_labels.py` rather than trusting a copied-in artifact -- the script and its output can silently drift apart.

## Data overlays: a separate concept from the base map's own categories

Overlays (historical/statistical layers laid on top of the map, toggleable independently of it — see `docs/OVERLAYS.md`) reuse the same multi-node-Scene/decal machinery as roads/water/parking, but are otherwise architecturally distinct from base-map categories: they're not tiled (built once as a handful of polygons, not per-tile like terrain/buildings), they're lifted much higher above the terrain (25mm for redlining and demographics vs. ~0.03mm for road/water/parking decals — `REDLINING_LIFT_MM` in `build_colored_disk.py`), and their meshes get `material.transparent = true` / `opacity = 0.5` in `template.html`'s `gltfLoader.parse()` callback (keyed on a node-name prefix check — `obj.name.startsWith("redlining_") || obj.name.startsWith("demo_")`, generalize further if a third floating overlay shows up) so they read as *layered on top of* today's map rather than replacing it. The `LEGEND_SECTIONS` entry for an overlay also carries a `note` field (rendered by `buildLegend()` as a `<p class="desc">` under that section's rows) for attribution/context text — used for the redlining layer's required CC BY-NC-SA citation, but worth adding for any overlay with real-world sourcing.

The demographics overlay (five Census ACS block-group metrics, see `docs/OVERLAYS.md`) is the first overlay with **continuous** values instead of a handful of fixed categories, and needed one real departure from the redlining template: each variable's 136 block groups are quantile-bucketed into 5 classes and colored from a sequential ramp, but unlike redlining's 4 separately-toggleable grades, all 5 buckets of one variable merge into **one** scene node — 25 individually-toggleable rows (5 variables × 5 buckets) would be unusable, so the toggle granularity is "show this variable," not "show this range." `site/template.html`'s legend gained a `row.ramp` option (a 5-color array instead of `row.color`) that renders a small gradient strip (`.ramp-swatch`) so the range is still visible without being individually toggleable — see `buildLegend()`'s `swatchHtml` branch.

## Highlight vs. visibility are two independent toggles per building category

Each building-category legend row has two separate controls, deliberately kept as different DOM elements (not nested inside one clickable `<label>`, to avoid fragile click-bubbling/`preventDefault` interactions): the checkbox+text `label` pair toggles `mesh.visible` (show/hide, removes it from the scene and from raycasting/collision entirely), and the colored `<button class="swatch">` toggles `setMeshHighlighted()` (grey out the category's real color without hiding it -- flips `material.vertexColors` off and sets a flat `UNHIGHLIGHT_COLOR`, `needsUpdate = true` since `vertexColors` affects shader compilation, not just a uniform value). A category can be un-highlighted and still visible, hidden and still "highlighted" (moot once hidden, but the state isn't cleared), or both -- the two are fully orthogonal. The "un-highlight all buildings" link at the top of the legend is just a convenience that loops over every `row.building: true` entry's swatch/mesh pair; it doesn't touch `visible` at all, and its own label text is derived by checking whether every building mesh already has `vertexColors === false`, not from separately-tracked state.
